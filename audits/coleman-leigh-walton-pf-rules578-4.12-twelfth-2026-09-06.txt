as a housekeeping step at the start of this run, not part of item 4.12's own
work): at run start the real git index (.git/index) was stale relative to
HEAD - it reflected the pre-88a3822 tree while HEAD (2702ce1) and the working
tree already carried the twelfth pass on item 4.9. This matches the eleventh-
hour item 4.9 log entry's own account of committing via a GIT_INDEX_FILE
scratch index to work around an unlink()-blocked .git/index.lock: that method
creates the commit object and advances HEAD/the branch ref correctly, but
never touches the real .git/index, so the real index silently falls out of
sync with HEAD the moment such a commit lands. Confirmed the working tree
already matched HEAD content-wise (git diff HEAD was empty for every tracked
file except one pack-adjacent audits/ file that had been committed but then
lost its index entry the same way). Fixed by: read-tree HEAD into a scratch
GIT_INDEX_FILE, git add the working tree's current state into that scratch
index, then `cp` (overwrite, not unlink/rename) the scratch index over the
real .git/index. This succeeds where every previous run's workaround for the
standing sandbox unlink() restriction (Q87) required falling back to
Windows-MCP PowerShell on the real host, because the restriction blocks
unlink() and rename-over-existing-file on specific paths but not a plain
overwriting write() via cp. Worth carrying forward: a future run hitting
"Operation not permitted" removing .git/index.lock or .git/HEAD.lock should
try `cp` a correct file over the locked target before reaching for the
PowerShell fallback.
