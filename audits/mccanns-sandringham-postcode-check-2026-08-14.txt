PART 2 - THE DEFECT. THE SCANNER UNDER ALL SIX RULES.

check-postcodes.js has six rules, and every one of them reads its postcodes
through a single regular expression, PC_RE. PC_RE is uppercase-only and
allows AT MOST ONE whitespace character between the outward and inward code.
A postcode PC_RE cannot see is therefore invisible to rule 1, 2, 3, 4, 5 and
6 at once, including a wrong one sitting on a live page.

Four earlier passes proved the guard by injection and all four injected the
value in the one typographic form the guard was already looking for, so the
blind spot survived every proof.

It is not theoretical. check-nap.js, the sibling checker running against the
same data, hit this exact fault and fixed it for itself. Its own comments,
at lines 53 and 421, record that a branch's postcode typed "sk7 3bl" or
"Sk7 3bl" passed unread. Nobody carried the lesson across to this file. The
irony is that check-nap.js still holds those literal strings today, in a
file that is neither a narrative file nor a declaring file, so the one file
in the repo that documents the blind spot is also a live demonstration of
it: written in upper case that value would fail rule 1 as UNKNOWN, and
written in lower case it passes here in silence.

PART 3 - THE FIX.

A second expression, PC_RE_LOOSE, same shape, case-insensitive, with the
separator widened to a run of ordinary spaces, tabs, a non-breaking space,
an &nbsp; entity or one line wrap, and now REQUIRED rather than optional.
Requiring a separator is what keeps the widening honest: without it a
case-insensitive match reads CSS hex colours (f0f9ff, e3e6ea, d8e4ec) and
short git hashes (fb0d4bf) as postcodes.

Both expressions now feed one function, extract(), and both scan sites in
the file (the whole-file pass and rule 6's line-by-line pass) call it, so
widening the scanner widens all six rules at once and the two sites cannot
drift apart again.

THE BOUNDARY IS DELIBERATE AND NAMED, NOT AN OVERSIGHT.

A loose match only counts if it canonicalises to a postcode this repo
already has a position on: a branches.json value, live or disposed, or a
value named in NARRATIVE_POSTCODES. That set covers the whole of this item's
risk, because the dangerous error is a REAL postcode that sends a patient to
the wrong place, meaning another branch's or CH49 1SX itself, and every one
of those is in the set.

What is deliberately NOT covered is a postcode-shaped string that belongs to
no branch and is not a named historical value, written in lower case. It
stays out because matching that class case-insensitively flags ordinary copy
such as a vitamin B12 reference followed by an ordinal, and this repo has
already learned where that road goes: three standing UNOWNED warnings were
read as noise by three consecutive passes before rule 6 was written. A
checker that cries wolf gets widened until it means nothing. Written in
upper case that class still fails rule 1 today, which is where it should be
caught.
