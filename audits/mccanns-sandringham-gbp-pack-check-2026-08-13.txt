THE DEFECT FOUND AND FIXED, IN THE CHECKER NOT THE PACK
tools/check-gbp-packs.js has a catchment rule that reads the ORDER of the
list and is structurally incapable of reading anything else. The regex it
matches with is composed out of the branch's own serviceAreaList towns, so
it can only ever match those towns. A town that is not on the list is not
read as a wrong element: it is invisible, and the run simply ends one
element early, still leading with the right seoTown, so the rule passes it
in both directions.

Proved by injection rather than asserted. The services-section catchment
"St Michael's, Aigburth, Lark Lane and Dingle" had Dingle replaced with
Woolton, a town this branch does not serve, and all 32 checkers stayed
green. That copy is pasted verbatim into a public Google profile, so it
claims a catchment the group does not have and aims the profile's local
search at a town none of the branch's own pages target.

The foreign-town rule further down the same file does not cover it: that
one fires only on a town that is ANOTHER branch's seoTown or
addressLocality, which is the sister-branch leak. A town belonging to no
branch at all falls between the two rules, and Woolton is exactly that.

A membership rule was added next to the order rule, composed from
branches.json so adding a town to a serviceAreaList permits that word for
that branch with no edit to the checker. It is deliberately membership
only, not completeness and not order: a pack may quote a shorter run than
the data holds, and the lead word is already owned by the rule above.

TWO FALSE POSITIVES ON FIRST RUN, BOTH FIXED IN THE RULE, NO PACK TOUCHED
The first version failed 16 times across 13 packs and every one was a rule
defect:
  1. The lead-in verb was swallowed. Every pack opens a run with "Serving
     Bootle, Sefton and Liverpool", so the first element read "Serving
     Bootle". The rule now reads the trailing words of an element too and
     takes the element as that town when a trailing phrase is one. This is
     not a loophole and was tested as such: "Serving Woolton" is still read
     as Woolton and still fails.
  2. An address is not a catchment. Both Ainsdale packs open "Sherwood
     House, Station Road, Ainsdale, Southport" and Riddings opens "Riddings
     Road, Timperley, Altrincham": comma separated, ending in the branch's
     own towns, the same shape as a catchment run and the opposite meaning.
     A non-own element ending in a street word is now skipped. Only
     non-own elements are tested this way, so "Lark Lane" is untouched
     because it is a real town in this branch's serviceAreaList.
