rank() (line 237) exists specifically because two branches.json entries CAN
legitimately share a postcode: Clear Chemist Aintree and head office are both
at Unit 20 Brookfield, L9 7AS, by design. rank() picks which one a message
should name when that happens - it does not distinguish that deliberate case

branch another live branch's real postcode, every one of the six generators
would propagate it faithfully into that branch's own pages, JSON-LD and map
queries, and every existing rule (1-6) would read the result as internally
consistent, because each one only ever compares a file to branches.json, never
branches.json's postalCode column to itself.

FIX
---
tools/check-postcodes.js:
- New var DELIBERATE_SHARED_POSTCODES, named next to rank()/byPostcode,
  listing the one legitimate case (L9 7AS: clearchemist_aintree +
  rbh_head_office_aintree) with a reason, same convention as every other
  KNOWN-style list in this repo (NARRATIVE_POSTCODES, NARRATIVE_FILES).
- New Rule 7 (DUPLICATE): groups all LIVE branches by normalised postalCode;
  any postcode held by 2+ live branches whose id set does not exactly match a
  DELIBERATE_SHARED_POSTCODES entry fails, naming the postcode and the
  branches sharing it.
- Staleness half, same convention as the NARRATIVE_POSTCODES stale-exemption
  check: a DELIBERATE_SHARED_POSTCODES entry whose named ids no longer match
  branches.json's actual live sharers of that postcode fails as STALE, so a
  future rename, disposal or address change cannot leave the excuse silently
  covering something it was never written to permit.
- Module header's Rules list updated to document rule 7.
