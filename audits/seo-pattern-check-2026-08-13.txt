2. THE DEFECT - THE ROLLOUT CONTRACT WAS READ BY NOTHING
   tools/seo-pattern.js declares PAGE_TYPES and describes it in its own
   comment as "the rollout contract for items 3.2 to 3.13 - every build
   script listed here must produce titles/H1s via the named functions,
   nothing hand-composed".

   git grep PAGE_TYPES across all tracked files returns three hits: the
   declaration, the module export, and one mention in AGENT_LOG.md. No
   checker, generator or test read it. The contract was documentation
   wearing the clothes of a guard.

   nothing in the repo could say so. Reverted.

   A first, cruder attempt at the same proof was rejected as unfaithful: a

   replica is the one that matters, because it is the realistic drift.

3. THE FIX - ALL IN tools/check-seo-pattern.js
   PAGE_TYPES is now read as DATA UNDER TEST, the same convention already
   used for the conditions read out of build-service-pages.js.

   Forward direction, per PAGE_TYPES entry:
     - a listed builder that does not exist FAILS
     - a builder that does not require ./seo-pattern FAILS
     - a title or h1 expression naming no function FAILS
     - a named function seo-pattern does not export FAILS
     - a builder that never calls its named function FAILS
   Reverse direction:
     - every tools/build-*.js must be named by a PAGE_TYPES entry or listed
       in KNOWN_NON_PAGE_BUILDER with a reason; an unlisted generator FAILS
     - a stale KNOWN_NON_PAGE_BUILDER key FAILS, whether the file has gone
       or has since been brought into the contract
   And an empty PAGE_TYPES FAILS rather than passing an empty loop.

   KNOWN_NON_PAGE_BUILDER holds two entries, both with reasons:
     build-status-page.js  - generates status/index.html, the internal
                             progress board, not a public branch page
     build-audit-status.js - publishes the audit status page to the data
                             portal, generates no branch page

   The alias is derived from each builder's own require line rather than
   assumed to be "pat", so a builder that names the import something else
   is read correctly instead of failing spuriously.

4. STATED LIMITATION, RECORDED IN THE CHECKER TOO
   The call check is textual and file-wide: it asks whether the builder
   calls the named function anywhere, not whether the specific title or H1
   leg does. Most builders call it twice, once for the page and once for the
   paste sheet, so inlining ONE of the two still finds the other and passes
   this rule. That residual case is late rather than silent: the output
   rules recompute every expectation from the live pattern functions, so the
   next change to seo-pattern.js makes the non-composing half stop matching
   and FAIL. What the new rule adds is the half nothing caught at all, which
   is contract rot, and a failure that names the generator at the moment it
   stops composing rather than surfacing later as an unexplained mismatch.
   This is written into the checker comment as well as here, so the next
   pass does not have to rediscover the boundary.
