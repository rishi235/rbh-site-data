ONE DEFECT FOUND, AND IT WAS LIVE-REACHING
See tools/check-seo-sheets.js for the full reasoning. In short: the estate
writes each page's two Weebly SEO fields THREE times - into the page's own
head comment, into a *-SEO.md sheet, and into a *INDEX.md paste manifest.
check-seo-sheets.js compared the first two. It read a NAMED list of six
*-SEO.md files, so the five INDEX.md manifests, carrying "SEO title" and
"SEO description" for 163 of the 177 pages, were compared to nothing.

Proved by injection, not by reading. The service INDEX.md row for
uti-treatment-smartts-bootle was changed to read "UTI treatment in Aintree -
Hirshmans Pharmacy": another branch, another brand, another town, on a
Smartts page. All 30 checkers passed. Whoever pastes works from whichever
sheet is open in front of them, so that string would have gone into the live
Weebly SEO title with no checker in between.

FIXED AT SOURCE, WITH THREE NEGATIVE TESTS
Sheets are now discovered rather than named, and each block is sorted into
one of two label dialects. Tests, each reverted with git checkout:

  INDEX.md SEO title naming another brand and town   -> FAIL, caught
  INDEX.md SEO description drifting by two words     -> FAIL, caught
  INDEX.md row pointing at a page that does not exist -> FAIL, caught

The switch manifest writes a non-ASCII arrow after its backticked slug and
the service manifest writes "->", so the slug is read from the backticks
alone: anything reading past the closing backtick covers one sheet and
silently drops the other. That was the trap in this parse and it is written
into the file so the next reader does not have to find it again.

All 163 INDEX rows were already correct once the injection was reverted, so
this closes a latent hole rather than a live breach. No copy was edited on
any page, sheet, pack or data field.

A THIRD APPARENT FINDING, DISPROVEN AT THE SHELL RATHER THAN IN THE FILE
A PowerShell pass over this run's own scripts appeared to show that their
dash-detecting character classes held the wrong characters, which would have
made every "no dash found" result above worthless. It was the shell, not the
files: PowerShell read the UTF-8 sources as ANSI, and the same mangling hit
the test string and the inline test regex together so they matched each
other. Re-tested inside node, with the dash characters built from their code
points so no shell touches them, the regex in the file matches a real em
dash, a real en dash and a &mdash; entity, and does not match a plain hyphen.
The dash results above stand. This is the same encoding trap the banner rule
was written for, met from the tooling side.
