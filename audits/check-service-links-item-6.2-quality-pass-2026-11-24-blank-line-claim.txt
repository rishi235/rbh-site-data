FRESH ANGLE
-----------
The seventeenth pass (2026-09-17) found and fixed a real gap: RULE 2 scanned
one physical line at a time, so a claim phrase hand-wrapped across two
ADJACENT lines ("...delivers" / "results...") was invisible to it. The fix
added a pairwise bridge testing each adjacent line pair (i, i+1).

That fix bridges strictly adjacent lines only. It does not bridge a claim
split by a BLANK (whitespace-only) line sitting between the two halves. This
is a different, equally realistic shape in the same file family: HTML
collapses a run of whitespace - including a blank line - to a single space
when rendered, so a paster who leaves a blank line in the middle of a <p> for
their own editing readability changes nothing a patient sees. It is no less
plausible than the adjacent-line wrap the seventeenth pass already found
live in this exact file's own lines 8-9.

Before testing check-service-links.js, the same question was checked against
the other two checkers that apply CLAIM_PATTERNS to prose rather than to a
single metadata field, to see whether either was already vulnerable to the
same shape:

  - check-weight-loss-copy.js RULE 9 runs CLAIM_PATTERNS against visible(p.raw),
    and visible() collapses an ENTIRE page's whitespace - blank lines
    included - into a single string (via collapse(): .replace(/\s+/g, " ")
    after tag/comment/script stripping) before any pattern is tested. A
    page-level split cannot be invisible to it, because the page is already
    fully joined by the time a pattern runs. NOT vulnerable.

  - check-gbp-packs.js's findClaims() runs CLAIM_PATTERNS against
    paragraphsOf(text), which already groups "runs of consecutive non-blank
    lines, broken at a blank line" and joins each paragraph's wrapped lines
    with single spaces (added on the item 4.5 seventeenth pass, 2026-09-11,
    for the identical reason: pack markdown hard-wraps at ~76 columns and a
    banned phrase can straddle that wrap). A blank line is already nothing
    more than a paragraph boundary to it, and a claim within one paragraph
    (however many physical lines it spans) is read as one joined string.
    NOT vulnerable.

check-service-links.js's RULE 2 had not been extended the same way as either
of the above, so this was the real, previously-untested gap.

FIX

tools/check-service-links.js, RULE 2's line-wrap loop. Before:

    for (let i = 0; i < lines.length - 1; i++) {
      if (claimHitLine.has(i) || claimHitLine.has(i + 1)) continue;
      const joined = (lines[i] + " " + lines[i + 1]).replace(/\s+/g, " ");

After:

    const nonBlank = [];
    lines.forEach(function (line, i) { if (line.trim() !== "") nonBlank.push(i); });
    for (let k = 0; k < nonBlank.length - 1; k++) {
      const i = nonBlank[k], j = nonBlank[k + 1];
      if (claimHitLine.has(i) || claimHitLine.has(j)) continue;
      const joined = (lines[i] + " " + lines[j]).replace(/\s+/g, " ");
      ...
      text: "lines " + (i + 1) + "-" + (j + 1) + " (" + pair[1] + "): " + joined...
    }

This is a direct generalisation: when there is no blank line between two
non-blank lines, j === i + 1 and behaviour is identical to the seventeenth
pass's fix. Only runs of pure whitespace are skipped over; a line that
itself carries content is never bridged past.
