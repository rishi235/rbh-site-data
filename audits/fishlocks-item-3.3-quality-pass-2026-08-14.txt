-----------------------------------------------------------------------
checkCrossTown() in tools/check-seo-pattern.js is the ABSENCE rule added on
the 2026-08-11 pass on this item, precisely because branches sharing a domain
compete for one catchment. It excused any town found in the branch's own
serviceAreaList:

    if (areas.indexOf(t.toLowerCase()) !== -1) return; // own catchment

There was no exception for a SISTER BRANCH ON THE SAME HOST. Three hosts
serve two live branches each:

    www.fishlockpharmacy.co.uk   fishlocks_ainsdale + fishlocks_eccleston
    www.mccannspharmacy.co.uk    mccanns_aigburth + mccanns_sandringham
    www.scorah-chemists.co.uk    scorah_bramhall + scorah_hazel

renders it into the public description as "Serving X, Y and Z". So ONE data
edit both commits the offence and buys the exemption that hides it. It is
self-cloaking and needs no code change.

WHAT THE RULE FOUND ON THE UNTOUCHED TREE, AND WHY IT IS PINNED NOT FAILED
-----------------------------------------------------------------------
The first version of the fix hard-failed the sister-town case. It fired on
the CLEAN tree, on three live pages:

  pharmacy-mccanns-sandringham.html  description names "Aigburth"
  pharmacy-scorah-bramhall.html      description names "Hazel Grove"
  pharmacy-scorah-hazel-grove.html   description names "Bramhall"

All three are geographically HONEST. Aigburth genuinely adjoins St Michael's;
Hazel Grove genuinely adjoins Bramhall. Fishlocks is clean in both directions,
its two towns being some 40 miles apart, which is why the injection had to
manufacture the case at all.

So this is not a defect with an obvious fix, and my first reading of it as one
was wrong. Removing the sister town makes the description less useful to a
patient searching the neighbouring district. Keeping it has two of our own
pages competing for one word on one domain. Which branch should own "Hazel
Grove" is a live conversion decision, the same class as the switch-banner
conflict this item's 2026-08-13 pass pinned to Q63 rather than deciding.
Shipping a checker that hard-fails the clean tree would also have broken every
subsequent run. RAISED AS Q71 and pinned.

THE FIX. tools/check-seo-pattern.js gains a shared-domain sister-town rule:
  - SISTER_TOWNS derived from hostMap, not a literal pair list, so a fourth
    shared domain is covered the day it is added.
  - A sister town is checked BEFORE the serviceAreaList excuse and is never
    excused by it.
  - KNOWN_SISTER_TOWN pins the three existing cases with a reason and Q71, on
    the same convention as KNOWN_DRIFT in check-cdn-pins.js: a listed case is
    reported and does not fail, anything NOT listed FAILS, and a listed case
    that has gone away FAILS as stale so the list cannot rot into a blanket
    exemption.
  - A missing hostMap fails. A hostMap yielding no shared host fails, because
    three exist today and a zero means either the derivation broke or the
    domains were genuinely split and the guard should be retired on purpose.
  - The per-brand summary line counts pinned entries separately, so the three
    do not read as three breakages on every future run.

The rule only ever REMOVES an excuse. It cannot make anything pass that
previously failed.
